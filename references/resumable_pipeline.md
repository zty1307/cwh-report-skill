## 1. 设计目标

正式报告不是一个长 Prompt，而是一条由确定性状态机管理的任务管线。用户侧仍是一键运行；后台必须做到：

- 中断后从失败节点继续；
- 已通过节点不重复执行；
- AI 未输出合格结构化产物时不能进入下游；
- 平台登录、等待 AI、等待人工复核属于正常等待状态，不等于整个任务失败；
- 每个节点可复现、可审计、可单独测试；
- 能用脚本完成的流程、计算、字段检查、文件校验和状态判断不交给模型。
- 默认以 `config/execution_policy.v1.json` 的 `bounded_60m` 档运行，总计3600秒，第2700秒停止继续消耗研究时间并保留交付时间。`bounded_40m` 为显式提速选项；需要穷尽检索时选择 `exhaustive`。缓冲不延长节点自身时限。

## 2. 唯一入口与节点

完整报告统一通过 `scripts/run_cwh_resumable_pipeline.py` 进入。不要再让模型自行决定先后顺序，也不要用一个 Codex Prompt 从数据导入一直执行到 Word。

固定节点如下：

1. `preflight`：在昂贵任务开始前检查依赖、模板和规则文件。
2. `intake`：固化议程、输入文件和输入指纹。
3. `workbook`：识别标准总表或将原始表转为经审核标准总表。
4. `research_plan`：按系统子议题生成检索任务、硬预算与证据口径。
5. `domestic_viewpoints`：境内媒体、自媒体和专家观点检索、原文快照及逐人原子观点。
6. `domestic_evidence_verification`：在独立第二遍模型运行中逐命题复核原文支持关系，生成不可绕过的映射审计和已验证观点包。
7. `domestic_comments_sentiment`：真实评论采集、正式引用审核和自有情感分析。
8. `overseas_evidence`：境外媒体与境外网民评论分开采集、翻译和审核。
9. `hotwords`：基于已审核证据提词、合并、自审和生成热词审核文件。
10. `render`：只消费上游合格产物，生成 Word、Excel、HTML 和结构化报告。
11. `delivery_gate`：检查正式门禁和成品一致性，之后才能归档。

这些节点可以独立测试，但正式流程必须由状态机按依赖关系调度。

`bounded_60m` 的标准总表输入在建档时自动将工作簿节点预算从900秒调为30秒，腾出的870秒分给境内观点节点（共1290秒）和独立复核（共600秒）。原始导出模式不变；评论、境外、渲染和总时限不变。预算写入首次契约，不能在旧任务上改时钟获得新预算。

## 3. 状态语义

- `pending`：尚未运行。
- `running`：正在运行。
- `retrying`：遇到明确的瞬时错误，正在自动重试当前节点。
- `succeeded`：产物存在、结构合格且哈希已登记。
- `waiting_ai`：已生成 AI 任务包，等待结构化审核结果。
- `waiting_login`：采集需要用户完成平台登录或提供获准的登录态。
- `waiting_review`：缺少业务元数据或需人工确认输入。
- `blocked`：上游或质量门禁阻止继续。
- `interrupted`：上次进程在节点运行中退出，可从该节点恢复。
- `failed`：确定性错误或重试后仍失败。

工作台不得把等待状态显示成“整个任务失败”，也不得把文件存在等同于节点成功。

## 4. 产物契约与质量门禁

每个节点只读取输入契约和上游登记产物。节点成功时记录：

- 输入指纹；
- 输出文件路径；
- SHA-256 哈希；
- 开始、结束时间；
- 尝试次数；
- 日志路径；
- 错误代码和下一步动作。

下游开始前重新检查上游文件和哈希。文件缺失、为空或被修改时，从最早受影响节点失效并重跑后续节点。

关键门禁包括：

- `analysis_bundle.json` 覆盖全部系统子议题，每个观点簇有成文说明和原始链接；
- 境内媒体检索按研究计划执行稳定来源通道和开放检索；`bounded_40m`、`bounded_60m` 达到通道覆盖及最低独立声音后，一轮无新增或预算耗尽即可停止，并将超出正文上限的有效候选留作 `reserve`；`exhaustive` 才要求逐来源与连续两轮无新增；
- 正式证据必须引用候选池中的合格 `candidate_id` 并记录代表性选择理由；每个发言主体单独通过原文忠实度和长度门禁，不能以合并多人或误识别“分析人士”等名词绕过；
- 每个合格候选保存带 SHA-256 的完整原文文本快照；每条成文观点使用唯一 `evidence_id` 映射文章标题、原始链接、单一发言主体、连续原文片段及字符位置，并由获准模型或人工把观点拆为逐条 `fully_supported` 命题；
- 评论必须是评论区真实原话，并包含平台、链接、评论标识和 AI 正式引用审核字段；
- 情感汇总的每个正式展示子议题状态为 `ready` 且分母大于零；
- 境外媒体和境外评论有独立采集审计，明确区分采集失败与完成但零结果；
- 热词审核满足证据、去重、议题覆盖和二次复核要求；
- `cwh_audit.json` 的 `ready_for_formal_delivery` 为真，Word、HTML 和结构化数据齐全；`domestic_evidence_mapping_audit.json` 必须通过，并确认同一映射完整进入 report_data、Word 和 HTML。
- 正式外媒附录只展示语义审核、简体中文门禁和去重后具有代表性的 TOP10；全部合格证据仍保留在结构化数据和工作台。

## 5. AI 节点纪律

AI 只处理语义相关性、观点聚类、评论质量、情感、翻译和热词代表性。固定结构、归因拼接、标点、编号和成品生成由脚本完成。状态机通过 `scripts/cwh_model_contract.py` 为每个 AI 节点生成 `tasks/<stage>.json`，包含：

- 本节点输入；
- 固定规则；
- 唯一输出路径；
- 结构化完成契约。

AI 只能完成当前节点，不得运行后续节点。输出后由脚本校验，AI 自称“已完成”没有效力。不合格结果自动退回当前节点，不允许用占位文字或说明文档冒充 JSON/CSV 产物。

模型不得修改 Skill 代码、验证器、`pipeline_state.json`、`pipeline_events.jsonl`、哈希或已完成报告。观点节点提交逐条 `formal_claim` 后，由 `scripts/normalize_cwh_analysis.py` 机械生成 `cluster.details`。不同模型只要遵守同一 JSON 契约即可接入。

若配置 `CWH_PIPELINE_AI_COMMAND_JSON`，状态机可调用获准的模型工作器自动执行 AI 节点；未配置时停在 `waiting_ai`，由当前 Agent 完成任务包后再次运行。同一状态协议不绑定供应商或模型家族。

## 6. 恢复、重试和失效

- 瞬时网络错误、API 429/5xx、超时可以只重试当前节点，并采用退避等待。
- 登录、验证码和账号风控不得自动绕过，转为 `waiting_login`。
- 语义审核不合格属于质量失败，保留问题清单并重做当前 AI 节点。
- 进程异常退出后，重新加载时将 `running` 改为 `interrupted`，随后从该节点继续。
- 显式修改上游数据、审核结果或规则版本时，使用 `invalidate` 从对应节点开始失效，下游全部重算。
- 等待用户、等待 AI 的次数不消耗失败重试额度。
- 失败节点在下一次显式 `run` 时重新开放本轮重试预算，并保留累计尝试次数；旧的成功状态若落后于追加式事件日志会被拒绝。
- 重试次数与时间预算分开计数：累计时间从首次 `run` 开始，包含等待 AI、登录和重试。节点预算从首次进入节点开始；`run`、`invalidate` 均不重置。超时写入 `time_budget_exhausted` 并保留断点，新一轮限时测试使用新的任务目录。
- 自动工作器只向当前 `declared_outputs` 写最终产物；种子、原始响应、预处理和批次文件写入任务声明的 `stage_workspace`。独立复核阶段的已验证观点包和映射审计由控制器生成，不在模型写入范围内。
- 草稿校验和最终审计统一调用 `cwh_viewpoint_gate.py`，完整的薄证据例外会保留在最终审计；不能靠重复来源、重复归因或填充字数绕过。

## 7. 测试与评估

每次规则修改必须运行：

1. 固定历史报告和人工确认样本组成的金标回归集；
2. 本轮真实业务新样本，检查泛化；
3. Bad Case 库，覆盖无意义评论、弱相关稿、匿名归因、镜像外媒、纯地名热词等边界；
4. 故障注入测试：中断、超时、缺文件、损坏 JSON、哈希变化、登录等待、AI 漏字段；
5. Word、Excel、HTML 和数据库归档一致性测试。

策略更新只有在历史金标不退步且新样本表现可接受时才能同步到正式 Skill 和 With 包。

40分钟是待实测验证的目标，适用于已具备来源访问能力与模型工作器的运行环境。真实原始工作簿处理、来源访问和模型响应均计时；过大的原始导出可能耗尽工作簿节点150秒预算，必须如实记录。跨模型验收同时报告完整交付成功率、失败节点和端到端耗时，不能将快速超时当成提速成功。默认40分钟档使用单工作器顺序执行，独立复核另开新的顺序运行上下文，不要求并发智能体；旧档位的并行提示并不代表已实现异步调度。

草稿提交后，控制器先用 `complete_cwh_evidence_structure.py` 补齐可唯一确定的缺失 ID、原文哈希和连续摘录定位，再归一化正文。已有错误字段保留给校验器，歧义不猜测，已冻结复核包不得重写。只读当前节点所需资料，复用已接受原文与产物；错误修复只改反馈字段，不让模型重写整篇报告。可用 `python scripts/cwh_timing_report.py --job-dir <任务目录>` 查看节点、命令耗时及未计量部分；该工具不统计 API token。

## 8. 命令行

命令默认输出精简 JSON：当前状态、任务路径、问题和节点状态表，避免每次续跑重复输出全部输入、哈希和历史。完整状态始终写入 `pipeline_state.json`；诊断或兼容旧 stdout 解析器时加 `--output-format full`。工作台服务读取的是完整状态文件，不依赖精简输出。

首次运行标准总表流程：

```powershell
python scripts/run_cwh_resumable_pipeline.py run `
  --job-dir outputs/cwh_pipeline_job `
  --agenda "7月10日国务院常务会" `
  --system-workbook "D:\path\CWH舆情情况.xlsx" `
  --execution-profile bounded_60m
```

查看状态：

```powershell
python scripts/run_cwh_resumable_pipeline.py status --job-dir outputs/cwh_pipeline_job
```

完成任务包要求的 AI 产物或平台登录后，重复执行 `run` 即从断点继续。若规则或上游结果有意修改：

```powershell
python scripts/run_cwh_resumable_pipeline.py invalidate `
  --job-dir outputs/cwh_pipeline_job `
  --invalidate-from domestic_viewpoints
```

随后再次执行 `run`；累计预算仍然有效。不要删除 `pipeline_state.json` 来伪造一次全新成功。升级前的旧任务若节点结构不兼容、状态与事件不一致或预算已经耗尽，应保留原任务作为失败审计，使用原始输入和新任务目录复测。

本地完整运行成功后，入口默认启动同一份可编辑工作台并写入 `workbench_launch.json`；自动化测试、With 容器和已有工作台后台调用必须传 `--no-open`，避免重复启动服务。
